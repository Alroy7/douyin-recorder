## 1. 需求①：UI 清新简洁

### 1.1 现状问题
当前 GUI（`src/gui.py`，790 行）是"能用"级别：系统默认 ttk 灰色主题、单窗口工具栏+表格+日志堆叠、无视觉层次、无搜索筛选、1000 行时信息过载、设置对话框是平铺表单。

### 1.2 方案 A（推荐）：保留 tkinter，做主题化重写

**设计语言（清新简洁）**

| 元素 | 规格 |
|---|---|
| 配色 | 背景 `#F6F8FA`、卡片 `#FFFFFF`、主色 `#22B5A6`（青绿）/ 辅助 `#4F8DF7`、文字 `#1F2937` / 次要 `#6B7280`、边框 `#E6EAEE` |
| 状态色 | 直播中 绿 `#10B981`、录制中 珊瑚 `#FF5A5F`、排队中 橙 `#F59E0B`、离线 灰 `#9CA3AF`、错误 红 `#DC2626` |
| 字体 | 中文 `Microsoft YaHei UI`；正文 10pt(≈14px)、表格行 34px、标题 12pt 加粗；等宽日志 `Consolas` |
| 圆角/留白 | 卡片 8px 圆角（Canvas 绘制）、卡片间距 12px、内容区左右留白 16px、表格无竖线、行高 34、斑马纹 `#FAFBFC` |
| 图标 | 用内置几何图形/Unicode 符号先做（✅ 不引入第三方图标库），状态用"圆点+文字 pill" |
| DPI | 启动时 `SetProcessDpiAwareness(2)` + `tk scaling`，4K 屏不糊 |

**布局（三区）：**

```
┌──────────────────────────────────────────────────────────────────────┐
│ 抖音直播录制                        [搜索主播/房间号]  ●在线  ●录制  ⏱今日 │  ← 顶栏 56px
├──────┬───────────────────────────────────────────────────────────────┤
│ 监控 │  全部 ▾  直播中 ▾  录制中 ▾            [开始监控] [立即检查] [＋添加] │
│ 记录 │ ┌───────────────────────────────────────────────────────────┐ │
│ 设置 │ │ 状态  主播名      房间号       清晰度   时长    大小   操作 │ │  ← 卡片表格
│      │ │ ●录制 张三        123456789   蓝光1080p 12:31  1.2GB  ⋯   │ │
│      │ │ ○离线 李四        987654321   —        —      —     ⋯   │ │
│      │ └───────────────────────────────────────────────────────────┘ │
│      │  [日志抽屉 ▾]  20:31:05  开始录制 张三 …                      │
├──────┴───────────────────────────────────────────────────────────────┤
│  CPU 3%  RSS 138MB  线程 12  队列 0  录制 3/10  今日流量 12.3GB   ⚙   │  ← 状态栏 26px
└──────────────────────────────────────────────────────────────────────┘
```

**功能增强（UI 侧）**
- 顶部搜索 + 快捷筛选（全部/直播中/录制中/排队中/错误）+ 按列排序；
- 表格只渲染当前筛选结果，超过 500 行自动分页（每页 100/200/500 可选）——实测 1000 行 Treeview 刷新只要 **4.3ms**，分页主要是为了人眼可读；
- 状态用 pill 徽章，录制中显示动态时长与实时文件大小；
- 双击主播：左侧详情抽屉（封面、标题、清晰度、输出目录、最近文件、日志），不再弹新窗口；
- 右上角"添加"：支持一次粘贴多行链接（批量添加）；
- 通知用右下角 toast（Win10 风格），不再打断操作；
- 设置页改为"左侧分组 + 右侧表单"（常规/录制/清晰度/通知/性能/账号/关于）；
- 可选：浅色/深色双主题（+0.5 天）。

**为什么不换 Qt/Electron**
- 无第三方依赖是我们当前的最大优势（用户机器上是 Python 3.13，无需 pip）；
- 实测 Treeview 1000 行性能足够（插入 4.8ms/更新 4.3ms/更新 50 行 0.2ms），瓶颈在视觉而非控件；
- Qt 需要 PySide6（~200MB 依赖 + 打包复杂），Electron 更重。

### 1.3 方案 B（可选二期）：本地 Web 面板
用标准库 `http.server` + SSE 暴露只读面板（HTML/CSS，可做真正的圆角/阴影/动画/响应式），浏览器打开 `http://127.0.0.1:8765`。
- 优点：视觉上限最高、手机同 WiFi 可看；
- 缺点：多一层服务与安全面、需要浏览器、开发 3–4 天；
- 建议：**先做 A**，若你觉得 A 的观感不够，再加 B（A 的主题变量可复用到 B）。

## 2. 需求②：1000+ 主播、长时间、稳、省内存

### 2.1 实测数据（决定架构的关键数字）

| 指标 | 实测值 | 含义 |
|---|---|---|
| 单房间 enter 接口延迟 | 0.15–0.9s（TLS 握手仅 0.033s） | 延迟主要来自服务端；连接复用收益有限，但省内存/句柄 |
| 在线房间响应体 | 776KB（gzip 后 **108KB**，≈7×） | 不压缩会让 1000 主播 sweeps 流量爆炸 |
| 离线房间响应体 | 48KB 原始 / **10KB** gzip；无效房间仅 108B | 离线轮询很便宜 |
| 1000 行 Treeview | 插入 4.8ms / 全量更新 4.3ms | UI 不是瓶颈 |
| 本机 | 20 核 / 32GB RAM（17GB 可用） | 资源充足，瓶颈在**带宽/抖音风控/磁盘** |
| follow 关注列表接口（匿名） | `status_code 20003 "User doesn't login"` | 批量查询必须登录（见需求④） |

### 2.2 调度器重写（核心，替代现在"每 tick 全量并发 4 线程"的实现）

现状：`manager.py` 每 `check_interval` 秒对所有主播并发查询（ThreadPoolExecutor 固定 4 线程）；1000 主播时会积压、无法限速、无熔断。

新设计 **Scheduler**：

1. **时间轮 + 优先队列**：每个主播有 `next_poll_at`，单调度线程把到期的房间丢进工作队列；固定 8/12/16 个工作线程（可配）消费。无"每房间线程"。
2. **全局令牌桶限速**：默认 `poll_rate_limit = 6 次/秒`（可配 1–20），带 ±20% 抖动；1000 主播一轮约 3 分钟。
3. **自适应轮询档位**（关键）：
   - 直播中 → 30s 复查（快速发现下播/断流）；
   - 最近 24h 开播过 → 90s；
   - 长期未开播 → 300s（可配上限）；
   - 每个主播单独退避（失败 30s → 5min 指数）；
   - 效果：1000 主播典型分布下 ≈ 4–6 请求/秒，既及时又不会触发风控。
4. **全局熔断**：连续 2 个窗口错误率 >30% → 暂停 30–120s + 刷新 ttwid + 降低速率；恢复后逐步提速（半开）。
5. **手动"立即检查"**：只把选中主播的 `next_poll_at` 提前，不动全局节奏。
6. **统计面板**：请求数/成功率/平均延迟/风控次数实时显示在状态栏。

### 2.3 网络层优化（改 `src/dy_api.py`，对外契约不变）

- 开启 **gzip**（`Accept-Encoding: gzip` + `zlib.decompress`）：实测在线房间 776KB → 108KB，1000 主播扫一轮流量从 ~100MB 级降到 ~10MB 级；
- **连接复用**：每线程一个 `http.client.HTTPSConnection`（keep-alive），省 TLS/句柄；失败自动重建；
- **响应上限与超时**：连接 5s / 读取 10s / 单响应 ≤2MB（防异常大包）；
- **解析后瘦身**：`LiveStatus.raw` 只保留必要字段（不保留 700KB 原始 JSON），避免内存驻留；
- 429/风控响应识别 + 冷却；cookie 缓存复用（现状已有，保留）。

### 2.4 录制并发：**不设硬上限**（用户 2026-11-13 澄清：1000+ 导入，开播都要录）

需求确认：用户是一次性导入 1000+ 直播间长期挂机，开播的要**同时**录，不是"同时只录 1–50 路"。因此设计改为：

- `max_concurrent` 默认 **0 = 不限**（可填 1–1000）；
- 并发不靠拍脑袋的数字，而由**三道资源闸门**自动调度：`max_total_mbps`（带宽预算，默认 0=不限）、`max_ffmpeg_processes`（进程/内存上限，默认 300）、`min_free_gb`（磁盘）。任一闸门不够 → 超出的房间显示"排队中"，闸门释放后自动开录；
- 轮询与录制是**两个独立调度器**：轮询按 6 req/s 限速 + 自适应间隔；录制进程各自独立，互不阻塞；
- UI 常驻显示：当前总带宽（估算）、录制路数、排队数、今日预计占用、磁盘剩余；设置页 0=不限 并给安全建议。

资源测算（原画 1080p ≈ 6.4 Mbps ≈ 2.9 GB/小时/路）：

| 同时录制 | 带宽 | 磁盘/小时 | 说明 |
|---|---|---|---|
| 10 路 | 64 Mbps | ≈ 29 GB | 家用宽带可承受 |
| 30 路 | 192 Mbps | ≈ 87 GB | 需要 500M/千兆宽带 |
| 50 路 | 320 Mbps | ≈ 145 GB | 千兆宽带 + 大硬盘 |
| 100 路 | 640 Mbps | ≈ 290 GB | 千兆也紧张，建议降清晰度（标清 1Mbps ≈ 450MB/h/路） |
| 300 路 | 1.9 Gbps | ≈ 870 GB | 理论值，家用不现实；设计上允许但会提示 |

结论：**软件不做人为限制**，但会用预算闸门和 UI 明确告诉你"当前能同时录多少、瓶颈是什么"；你也可以把预算设为 0 让它真不限（后果自负，UI 会标红提示）。

### 2.5 长时间稳定性（7×24）

| 风险 | 措施 |
|---|---|
| 内存缓慢增长 | 历史记录改 SQLite（标准库）；事件/日志环形缓冲；每小时自检 RSS/句柄并写指标 |
| 监控线程卡死 | 独立 watchdog 线程监测心跳，>3×间隔无心跳则重启监控 & 通知 |
| ffmpeg 僵死/残留 | 现有卡死看门狗保留 + 句柄/进程数巡检 + 退出 taskkill 兜底 |
| 日志膨胀 | 5MB×3 轮转；轮询明细降 DEBUG；状态变化才 INFO |
| 抖音接口变更 | 协议层集中 `dy_api.py`，启动自检一次（拿 feed 验证），失败时 UI 明确提示"协议可能失效" |
| 电脑重启/断网 | 可选开机自启（启动.bat 放 Startup 或计划任务）；断网期间退避，恢复后自动继续 |

**浸泡测试（验收）**：本机起一个 mock 服务器模拟 1000 主播（90% 离线/10% 在线、真实响应体大小、随机延迟、偶发错误）+ 10 路模拟流，跑 24h，记录 RSS/句柄/CPU/丢录；验收线：RSS 增长 <10%、无句柄泄漏、idle CPU <5%（单核）、开播检测 P95 ≤ 设定间隔+30s。

## 3. 需求③：清晰度选择，默认最高

### 3.1 实测发现（重要）

房间响应的 `stream_url.live_core_sdk_data.pull_data.options.qualities` 里有**精确的清晰度元数据**（匿名即可拿到，`disable=0` 表示可用）：

| 实测样例 | name | sdk_key | resolution | 码率 | fps |
|---|---|---|---|---|---|
| 房间A | 标清/高清/超清/蓝光/原画 | ld/sd/hd/uhd/origin | 960x540 … 1920x1080 | 1M / 2M / 6M / 6.4M | 25–60 |
| 房间B（竖屏） | 标清…蓝光/原画 | ld/sd/hd/uhd/origin | 540x960 … 1080x1920 | 1M…8.8M | 25–59 |
| 房间C（4K 横屏） | 标清…蓝光 | ld/sd/hd/uhd | 1280x1280 … 3840x3840 | 4M/6M/8M | 30 |

注意坑：不同房间的 `origin/uhd` 语义不一致（有的房间"蓝光"就是 origin），flv 档位名 `SD1/SD2` 与 `ld/sd` 存在交叉映射，**不能按档位名硬编码**。

### 3.2 设计

1. **质量表构建**：对每个在线房间解析 `qualities[]` → 生成候选列表（name, sdk_key, 分辨率, 码率, fps, disable）→ 映射到实际 flv/hls URL（优先 flv）。
2. **默认策略 `best`（默认，跟随最高）**：按（分辨率面积, 码率, fps）排序取最高；UI 显示实际档位与分辨率（如"蓝光 1920×1080 6.4Mbps"）。**满足"默认最高清晰度"**。
3. **每主播覆盖**：跟随最高 / 原画 / 蓝光 / 超清 / 高清 / 标清 / 仅音频（若房间提供 ao 档）；缺失自动向下回退。
4. **自动降档**：同一场次断流+卡死 ≥2 次 → 下调一档（原画→蓝光→超清→高清），并在该场次保持；下播后恢复用户设定（可配"记住降档结果"）。
5. **仅音频**（省带宽）：`-vn` 录制，可选。
6. **验收**：抽 20 个在线房间，验证"选出的 URL 实际分辨率/码率 = 目标档位"一致率 100%；断流场景验证降档生效且 UI 显示。

## 4. 需求④：需要登录抖音号才能录制吗？

### 4.1 直接回答：**不需要**

- 匿名 `ttwid` 就能查直播状态、拿 flv/hls 地址；
- 实测匿名拿到 1080p（1920×1080 6.4Mbps）甚至 4K（3840×3840）档位，`disable=0`；
- 已用匿名流完成 60 秒/30 秒真实录制（ffmpeg 可解码播放）。
- 所以"录制"这件事，**不登录也能做**。

### 4.2 登录能带来什么（1000+ 场景价值很大）

| 收益 | 说明 | 实测/依据 |
|---|---|---|
| 批量查"关注列表在播" | `/webcast/web/feed/follow/` 一次请求返回所有关注主播的在播状态，1000 主播从 1000 次请求降到 1 次（+ 只在播房间的取流请求） | 匿名调用返回 `20003 User doesn't login`，已实测 |
| 更低风控 | 登录态请求更像真实用户，限流阈值更高 | 社区经验，未实测 |
| 部分房间/档位 | 个别房间对匿名用户隐藏高码率或限制访问（`disable=1` 的档位、付费/私密直播） | 逻辑依据，未实测 |
| 粉丝团/连线内容 | 部分内容仅登录可见 | 平台规则 |

### 4.3 登录的代价与风险

- Cookie = 账号登录态，泄露等于账号被控；
- 自动化轮询有风控风险（尤其 1000 主播高频请求），可能触发验证码/限流/临时封禁；
- 多设备登录提示、账号安全提醒；
- **建议：只用小号、只在工具内本地加密存储、只读公开信息、不做点赞/评论/关注等写操作。**

### 4.4 实现方式（推荐顺序）

1. **浏览器 Cookie 粘贴导入（推荐，v1 只做这个）**：用户在浏览器登录抖音 → F12/扩展导出 Cookie → 粘贴进「设置→账号」；工具解析 `ttwid/sessionid/sid_guard` 等关键字段；
   - 用 **Windows DPAPI**（`CryptProtectData`，ctypes 调用）加密存本地文件，绑定当前用户，换机/换用户无法解密；
   - 日志/界面只显示"已登录（昵称/uid，若可查）"，不打印 Cookie。
2. **本机浏览器 Cookie 自动读取**：需要解密 Chrome/Edge 的 cookie 库（DPAPI + ABE），实现复杂、杀软敏感，**不做**。
3. **扫码登录**：需要模拟官方登录流程 + 验证码/滑块，风控高、维护成本大，**不做**。

### 4.5 运行时策略（混合模式）

- 未登录：全部走单房间轮询（当前已验证方案）；
- 已登录：若"关注"里覆盖了 N 个主播 → 用 follow 批量接口刷在播状态（间隔可 60–120s），只对**在播**的主播调 enter 取流；未关注的主播仍走单房间轮询；
- 效果：1000 主播中 900 个已关注时，每轮请求数从 1000 降到 ~100（约 90% 降幅）；
- 风控失败自动回退到匿名轮询，UI 提示。

## 5. 分阶段计划与验收

| 阶段 | 内容 | 预估 | 验收标准 |
|---|---|---|---|
| P1 | 调度器 + gzip + 资源治理 + SQLite 历史 + 指标面板 + 24h 浸泡 | 3–4 天 | 1000 主播 mock 浸泡 24h：RSS 增长<10%、无句柄泄漏、idle CPU<5%、检测延迟达标 |
| P2 | UI 清新重构（方案 A）+ 搜索/筛选/分页/详情抽屉/toast/设置页 | 2–3 天 | 1000 行操作流畅；你看截图确认"清新简洁"；深浅色可选 |

## 5.5 新增需求（用户 2026-11-13 追加，已开工）

### A. 过短录制自动删除
- config：`min_keep_seconds`（默认 30，0=关闭）；
- 判定：一场直播的总录制时长（多段合计 / remux 后）< 阈值 → **删除该场全部产物**（含 ts/flv/mp4/sidecar），写运行记录（deleted=1），并在日志/通知里提示「过短录制已删除（12s < 30s）」；
- 边界：正在写的文件不删；remux 失败但时长足够则保留原文件；删除不会误伤磁盘清理任务。

### B. ffmpeg 自动检测 + 缺失提示下载
- 检测链：config → `<项目根>/bin/ffmpeg.exe` → 原软件目录 → PATH → 常见安装目录（C:/ffmpeg、LOCALAPPDATA、Program Files、choco/scoop/winget）→ 注册表 App Paths；
- 缺失时：`python run.py --check` 输出下载地址与放置说明；GUI 设置页显示「未找到 ffmpeg」+「下载 ffmpeg」按钮（打开 gyan.dev builds 页）+「手动选择文件」；
- **不自动下载/安装**（按你的要求只提示）。

### C. 运行记录保存（供你多天后发我分析）
- 日志：`logs/run-YYYY-MM-DD.log` 按天分文件，`log_keep_days`（默认 30 天）自动清理；
- 数据库：`data/history.db`（SQLite，标准库）记录每场录制（主播/房间/清晰度/开始结束/时长/大小/路径/状态/是否删除）、每次运行、每个错误；
- UI「运行日志」页：按日期/主播/状态筛选，支持导出；
- CLI：`python run.py --history --days 7`；
- **一键导出诊断包**：`python run.py --export-diagnostics out.zip` → 含脱敏配置、最近 N 天日志、历史统计、ffmpeg/系统信息，zip 直接发给我，我据此找改良点。

### D. 打包免 Python 的 Windows exe
- PyInstaller **onedir**（比 onefile 启动快，且要带 87MB ffmpeg）：`dist/DouyinRecorder/` + `dist/DouyinRecorder_win64.zip`，解压双击 `DouyinRecorder.exe` 即可，配置/输出目录基于 exe 同目录；
- 体积约 95MB（含 ffmpeg），未签名 → 首次运行 SmartScreen 提示「更多信息→仍要运行」，杀软误报加信任即可；
- 仅支持 Windows 10/11 x64；构建脚本 `build/build.ps1` 可复现；
- 目标机器无需 Python、无需联网安装依赖。

## 6. 需要你拍板的 7 件事

1. UI 方案：**A（tkinter 主题化，推荐）** / B（本地 Web 面板） / 先 A 后 B？

6. 阶段顺序：先 UI（P2）还是先性能（P1）？
7. 你的日常规模：1000+ 是"长期挂机监控"还是"同时录制很多场"？（影响并发/带宽默认值与硬盘规划）

## 7. 风险与边界

- 抖音接口/风控随时可能变，方案已做"协议层集中 + 启动自检 + 熔断"来降低维护成本；

- 录制版权归主播/平台，工具仅供个人备份；
- 不做任何授权破解/绕过；登录仅使用你自己的账号 Cookie 查询公开直播信息。
